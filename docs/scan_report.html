Read-through of SqliteConn.cpp (schema, triggers, receipts, joint charges) and Money.h. I didn't build or run the tests. Scanned 17 Nov 2026.

How the money pipeline works

charges←allocations→payments→receipts→audit_log (hash chain)
  • charges are what is owed (amount_due). Triggers keep amount_paid and balance in sync, computed in integer cents.
  • payments are money that came in or went out (direction in/out). Any part of a payment that isn't allocated counts as the client's credit.
  • allocations link payments to charges. Triggers stop an allocation from going over the payment or the charge, or crossing directions.
  • receipts number is MAX+1 per series. A receipt needs its payments fully allocated, and one receipt can only cover one client and one batch. Once issued, a receipt can't be deleted, and it freezes its payments, their allocations and the charges they settle. To undo one, you void it with a reason.
  • joint charges (κοινόχρηστα) are a joint_ops record plus fixed joint_shares. The shares have to add up exactly to the total, and every excluded apartment needs a reason.
  • audit_log is append-only and hash-chained. A checkpoint is written daily to backups/*_audit_anchor.txt, and the chain is checked at startup.

Solid already

Good

The maths adds up. All the sums I looked at are done in integer cents, in C++ and in SQL triggers alike. Money parsing rejects ambiguous input such as 1,234 or a third decimal. Joint shares and receipt totals must match exactly, and multi-step writes run inside savepoints. I found no rounding drift in the code I read.

Weak points, most important first

HighReceipt number and date can disagree

The number is MAX(number)+1, but issue_date is whatever the user types, and nothing checks it is on or after the previous receipt's date. So receipt A-10 can be dated before A-9. Greek bookkeeping (and later myDATA) expects numbering and dates to be chronological within a series. Fix: refuse any date earlier than the last issued receipt in the same series.

HighNo VAT or tax model yet, so receipts aren't legal documents

Charges have no nature, VAT rate or net/VAT/gross fields. The company has no ΑΦΜ/ΔΟΥ and clients have no ΑΦΜ. These are roadmap steps 1–3. Until they're done, what the app prints are internal collection notes, not ΑΠΥ/ΤΠΥ.

HighNo login or roles

There's an actor column but no authentication. Anyone at the PC can void receipts or use the SQL console. For a "really good logger" the log has to say who did each thing, so you need at least local users with a PIN, and the SQL console limited to admins.

MediumBackups and the audit anchor sit on the same disk as the database

Backups go to backups/ next to data.db, so one disk failure takes out everything. The tamper anchor is in that same folder too, so anyone who can edit the database can rewrite the anchor as well. Add a second backup target (USB drive or cloud folder) and offer an export of the anchor file.

MediumSeveral rules exist only in C++, not in the database

These rules are only checked in the app: receipt total equals the sum of its payments, one client per receipt, and joint shares summing to the total. The SQL console or any future server goes straight past them. Also, charges.amount_due has no CHECK ≥ 0 and charges.status is free text with no CHECK IN (…). Add triggers or CHECKs for these.

MediumMoney is stored as REAL

It's safe for now because every write snaps to whole cents and every sum casts to cents. But a raw SQL write can still store 10.005. Before online payments arrive, move these columns to INTEGER cents. That's one migration, and you already have the migration framework for it.

MediumvoidReceipt has leftover code

It runs a single UPDATE with no savepoint, then computes ids and now and never uses them. That looks like a step that got deleted, probably an audit entry or unlocking the payments. Check that a void still writes an audit row that includes the reason.

LowCode and repo hygiene
  • App.cpp is about 17k lines and SqliteConn.cpp about 8.6k. The migrations live inside the constructor, and the same trigger blocks are repeated across schema versions.
  • Files committed that probably shouldn't be: RELEASE-V1.zip, the .db files, an mp4, SqliteConn.cpp.bak_before_partnerfix and imgui.ini.
  • Recent commit messages are just "transferring fixes", so the history doesn't explain what changed.

Suggested order

  • Check that receipt dates are chronological, and fix up voidReceipt. Both are small.
  • Add the missing CHECKs and triggers on charges and receipts.
  • Add local users and PINs, and put real names in the audit actor.
  • Add a second backup location.
  • Then roadmap steps 1–3 (nature, tax details, VAT), followed by the switch to INTEGER cents.
